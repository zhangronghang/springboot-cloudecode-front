## Context

当前城市路由为 `/province/:province/city/:cityCode`，对应页面仅加载区县边界。图片服务只提供通用图片元数据和文件管理接口：上传、列表、详情、更新与删除；列表仅能按单个标签关键字模糊匹配，且图片内容需要通过详情接口以 Base64 获取。具体目标见 [proposal.md](proposal.md)。

## Goals / Non-Goals

**Goals:**

- 将通用图片记录稳定映射为可按城市查询的个人足迹。
- 使网络请求、受管理标签和页面展示彼此隔离，并可独立测试。
- 在不修改后端的前提下提供完整的图片增删改查体验。

**Non-Goals:**

- 不新增后端的城市足迹、账户或多图片相册模型。
- 不实现登录、跨用户数据隔离、离线缓存、图片压缩或批量上传。
- 不改变现有地图加载和区县边界浏览行为。

## Decisions

### 用受管理标签存储城市与日期

市级记录写入 `city:<六位城市编码>`，区县记录写入 `county:<六位区县编码>`，每条记录均写入 `visited:YYYY-MM-DD`。当前行政区以其层级标签调用列表接口；日期、归属和自定义标签由前端统一解析。用户输入的标签不得覆盖或伪造 `city:`、`county:`、`visited:` 前缀。

选择该方式是因为现有接口可按标签检索且无需后端变更。相比把结构化信息拼入描述，它保留了按行政区筛选能力；相比新增后端实体，它的实施范围更小。代价是后端无法同时按行政区和日期查询，日期筛选留给前端后续扩展。

### 以一张图片作为一条足迹记录

创建必须选择一张图片；标题和日期为必填，感受和自定义标签可选。编辑使用同一图片记录 ID，只有选择新文件时才替换图片。该模型严格匹配后端的一条图片记录及其元数据，避免维护不存在的足迹父实体。

### 建立独立的图片 API 与足迹映射层

新增 API 客户端封装统一响应、JSON 请求和 `FormData` 请求；新增领域工具负责生成、解析和验证受管理标签。城市页面及其子组件只接收足迹领域对象和用户操作结果，不直接拼接 HTTP 参数。

该边界能使标签协议和接口失败处理在单元测试中验证，也避免路由参数、表单状态和网络细节相互耦合。

### 通过开发代理访问后端

开发环境将 `/api` 代理至 `http://localhost:8081`，浏览器请求保持同源路径。生产部署由其宿主反向代理或部署配置提供同等路由。

该选择避免依赖后端跨域配置；替代方案是把完整后端地址写入页面，但这会使开发与部署环境耦合且可能触发跨域限制。

### 按需加载图片详情

列表接口返回元数据后，前端对当前页记录请求详情以取得 Base64 图片内容，并限制页面大小以控制并发请求。单条详情失败不会阻止其余元数据显示，图片位置显示可重试占位。

选择按需详情是因为后端未提供图片 URL 或缩略图字段。替代方案是修改后端列表接口返回缩略图，但这超出本次“不改后端接口”的范围。

## Risks / Trade-offs

- [标签协议被其他客户端未按约定写入] → 解析时只接受当前层级的精确 `city:` 或 `county:` 标签和有效日期格式；异常记录不作为正常足迹展示。
- [列表页逐条加载 Base64 导致请求较多] → 使用分页、限制默认页大小并让单条失败独立降级。
- [图片 Base64 造成页面内存增长] → 离开页面或切换分页时释放本页对象 URL/内存引用。
- [后端业务错误以 HTTP 200 返回] → API 客户端同时校验 HTTP 状态与响应 `code === 200`。

## Migration Plan

1. 部署前端时同步配置开发代理或生产反向代理的 `/api` 转发规则。
2. 新创建和编辑的记录立即遵循标签协议；已有未带 `city:` 标签的通用图片不迁移，也不显示为城市足迹。
3. 回滚时移除城市足迹 UI 与前端请求模块即可；后端图片数据保持不受影响。
